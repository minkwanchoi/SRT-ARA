# 예외사유 표기법

「무기체계 소프트웨어 신뢰성 시험에서 예외사유의 효율적 관리 방안」(서지 사항은 README의 '참고문헌') 표 1의 표기법을
SRT-ARA(내부 이름 `srtgen`)가 해석하는 문법으로 확정한 것이다. 시험 유형마다 식별 문자와 쓸 수 있는
항목이 다르며, 각각 매뉴얼 부록 7의 다른 양식(부록 7-24~26쪽)으로 출력된다.

## 1. 형식

```
/*SRT-S-C-ID##-1{Comments}*/
   ①        ②   ③    ④
```

| 구분 | 내용 |
|---|---|
| ① 시험 유형 | `S-C` 정적시험-코딩규칙, `S-W` 정적시험-취약점점검, `S-M` 정적시험-소스코드메트릭, `D` 동적시험 |
| ② `ID##` | 예외사유 고유 번호. 시험 유형별로 따로 매긴다 |
| ③ `1~N` | 예외사유 인덱스. `1`은 결함이 검출된 위치, `2~N`은 사유 설명에 필요한 다른 위치의 코드 |
| ③ `START`, `END` | 인덱스 뒤에 붙이면 여러 줄 범위의 시작과 끝 |
| ④ `{Comments}` | 예외사유 내용. `@항목{내용}`을 나열한다 |

- 식별자는 소스에 쓴 그대로 보고서의 "코드위치(주석정보)"에 나온다. 보고서의 식별자로 소스를 검색해
  위치를 찾으므로, 한 ID는 한 가지로 쓴다(`ID01`과 `ID1`을 섞어 쓰면 같은 ID로 묶되 경고한다).
- 주석 형식은 `/* */`와 `//` 모두 쓸 수 있다. `//` 주석은 본문의 중괄호가 닫힐 때까지 이어지는 `//` 줄을 한 덩어리로 본다.
- 본문은 `START`, `END`, 단독 태그 어디에 붙여도 된다.
- `@항목` 없이 내용만 쓰면 그 유형의 사유 항목(`@FA분석` 또는 `@미달성사유`)으로 본다.
- 내용이 여러 줄이면 한 문단으로 합친다. 빈 줄 또는 `\n`은 줄바꿈으로 남는다.
- 내용에 중괄호를 쓸 때는 짝을 맞추거나 `\{`, `\}`로 쓴다.

## 2. 가리키는 코드

| 쓰는 방법 | 발췌되는 코드 |
|---|---|
| 코드와 같은 줄에 단독 태그 | 그 줄 |
| 주석만 있는 줄에 단독 태그 | 바로 다음 코드 줄 |
| `START` ~ `END` | 두 태그 사이. 태그가 코드와 같은 줄에 있으면 그 줄을 포함한다 |
| `S-M` 단독 태그 | 태그가 속한(또는 바로 뒤의) 함수의 선언부 |

발췌한 코드에서 표기법 주석은 지워진다. 파일명, 함수명, 줄 번호는 도구가 채운다.

```c
uint32_t motor_wait_mode(uint32_t mode)
{
    uint32_t u_res = 0u;
    do {                                    /*SRT-S-W-ID1-1START*/
        u_res = get_value(mode);
        delay_ms(1000u);
    } while (0u != u_res);                  /*SRT-S-W-ID1-1END{
        @취약점{Potential Unbounded Loop}
        @Ref{CWE-835 Loop with Unreachable Exit Condition ('Infinite Loop')}
        @설명{사용자가 선택하는 모드를 수신하기 위해 무한루프로 대기하는 코드이다.}
        @FA분석{개발자가 의도적으로 사용한 무한루프를 시험도구가 검출한 것이다.}
        @결론{모드 수신 대기 기능은 integration test 에서 정상 동작을 확인하였음.}
    }*/
    return u_res;
}
```

## 3. 동일사항

같은 사유가 여러 곳에 해당하면 **같은 ID의 인덱스 1**을 각 위치에 다시 쓴다.
본문을 쓴 위치가 대표가 되고 나머지는 양식의 "동일사항" 표에 들어가며, "개수"는 자동으로 센다.
동일사항 위치에는 위치마다 다른 항목(`@비고`, `@측정값`)만 쓰면 된다.

```c
if (stamp == (time_t)-1) {              /*SRT-S-C-ID1-1{@비고{주기 점검 경로}}*/
```

```cpp
// SRT-S-C-ID1-1
if (now == static_cast<std::time_t>(-1)) {
```

## 4. 시험 유형별 항목

괄호 안은 같은 뜻으로 받아들이는 이름이다(논문 예시의 `@위반 유형`, `@Ref.`, `@사유` 포함).
항목 이름의 공백과 마침표는 무시한다. **굵은 글씨**는 없으면 경고가 나오는 항목이다.

값의 기준은 「무기체계 소프트웨어 개발 및 관리 매뉴얼」, 방위사업청 매뉴얼 제2024-6호(개정 : 2024. 12.26.)의
부록 7 '3. 시험기준'(부록 7-10~12쪽, 동적시험은 부록 7-13쪽)과 코딩 규칙 기준을 정한 부록 6의 관련표준(부록 6-2쪽)이다. 기준에 정해진 값은 확인·편집 화면에서 목록으로 고를 수 있다.

**근거는 규칙 번호와 규칙명까지만 적는다.** 이 도구는 규칙을 분석하지 않는다(코드가 규칙을 어겼는지 판단하지 않는다).
번호와 이름의 출처는 다음과 같다.

| 기준 | 번호·이름의 출처 | 도구에 든 목록 |
|---|---|---|
| CWE | https://cwe.mitre.org/data/definitions/658.html (659, 660) | 번호와 이름. 번호만 적으면 이름을 채운다 |
| C++ Core Guidelines | https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines.html (개인·내부 업무용만 허락) | 공개본에는 없다(라이선스). 원본을 보고 규칙 목록 창에 직접 넣거나 CSV로 불러오면 번호(ES.20 등)로 고를 수 있다 |
| .NET Framework Design Guidelines | .NET 코드 분석 품질 규칙 https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ (설계 규칙이 이 지침을 따른다고 Microsoft 문서가 밝힘) | 규칙 번호와 규칙명 335개(CA1000 등, 같은 표의 IL3000 등 포함). 번호만 적으면 규칙명을 채운다 |
| MISRA C, MISRA C++ | https://misra.org.uk/publications/ (구매 문서, 1인 사용 허락. 공개된 규칙명 목록 없음) | 없음. 번호와 규칙명을 직접 적는다 |
| Code Conventions for the Java Programming Language | https://www.oracle.com/java/technologies/javase/codeconventions-contents.html (1999년판. 비상업·회사 내부 사용만 허락) | 공개본에는 없다(라이선스). 원본을 보고 규칙 목록 창에 직접 넣거나 CSV로 불러오면 `@규칙{7.5}`처럼 절 번호로 고를 수 있다 |
| C# Coding Conventions | .NET 코드 스타일 규칙 https://learn.microsoft.com/dotnet/fundamentals/code-analysis/style-rules/ | 규칙 번호와 규칙명 130개(IDE0001 등). 번호만 적으면 규칙명을 채운다 |

확인·편집 화면의 설정 메뉴 "규칙 목록…" 창에서 기준을 고르면 도구에 든 목록(CWE 포함)을 보고 찾을 수 있다. 도구에 목록이 없는 기준은 이 창에 번호와 규칙명을 넣어 두면 편집할 때 고를 수 있다.
직접 넣은 목록의 규칙명은 고를 때 주석의 `@FA내용`에 적힌다(보고서를 만들 때 이 목록에서 찾아 넣지 않는다).

| 시험 | 기준 |
|---|---|
| 코딩규칙 검증 | MISRA-C:2012, MISRA-C:2023, MISRA-C++:2008, MISRA-C++:2023, C++ Core Guidelines, Code Conventions for the Java Programming Language, C# Coding Conventions, .NET Framework Design Guidelines |
| 취약점 점검 | 소프트웨어 취약점 점검(CWE-658 C 103개, CWE-659 C++ 97개, CWE-660 Java 84개)과 보안약점 점검 목록(CWE 44개) |
| 소스코드 메트릭 | 사업의 신뢰성시험계획에서 정한 종류와 제한값(시험 기준의 예: Cyclomatic Complexity, Number of Call Levels, Number of Function Parameters, Number of Calling Functions, Number of Called Functions, Number of Executable Code Lines) |
| 동적시험 | 코드 실행률: 문장(Statement), 분기(Branch), MC/DC |

각 양식으로 만드는 보고서는 매뉴얼이 시험확인서에 따로 첨부하게 한 자료(부록 7-12, 7-16)다. 유형마다 근거를 제목 아래에 적었다.

### S-C 코딩규칙 → 코딩규칙 점검 FA 사유서

매뉴얼 근거: 거짓경보 설명자료(부록 7-12 5. 가). 시험도구가 결함으로 검출했지만 실제 오류가 아니거나 기능 구현에 꼭 필요한
코드임을 `@FA분석`에 적는다(거짓경보의 정의는 부록 7-8).

| 항목 | 양식의 칸 |
|---|---|
| **`@기준`** (코딩기준, 표준) | 코딩규칙 칸의 첫 줄. 적용한 코딩규칙 기준(`MISRA-C:2012` 등). 위 표에 없는 값이면 경고 |
| **`@규칙`** (규칙번호, 코딩규칙, 위반유형) | 코딩규칙 칸의 둘째 줄. 규칙 번호(`Rule 14.3`, `ES.20` 등) |
| **`@FA내용`** (규칙명, 내용) | FA내용. 규칙명을 적는다. 도구에 그 기준의 목록이 든 C# Coding Conventions, .NET Framework Design Guidelines는 비워 두어도 번호로 찾아 채운다. 그 밖의 기준(MISRA 등)은 직접 적거나, 규칙 목록 창에 넣어 둔 목록에서 고르면 그때 규칙명이 주석에 적힌다 |
| `@설명` | 코드내용 아래 설명 |
| **`@FA분석`** (분석, 사유) | FA분석 |
| **`@결론`** | 결론 |
| `@Ref` (참조) | 코드내용 아래 참조 |

### S-W 취약점점검 → 취약점 점검 FA 사유서

매뉴얼 근거: 거짓경보 설명자료(부록 7-12 5. 가). 코딩규칙과 같은 양식이다.

| 항목 | 양식의 칸 |
|---|---|
| **`@취약점`** (위반유형, CWE) | 취약점. `CWE-476 NULL Pointer Dereference`처럼 CWE 번호를 적는다. `@취약점`과 `@Ref` 어디에도 CWE 번호가 없으면 경고 |
| `@FA내용` (취약점명, 내용) | FA내용. 쓰지 않으면 CWE 번호로 이름을 찾아 채운다(보안약점 점검 목록의 표기가 먼저, 없으면 CWE-658/659/660의 이름). 어느 목록에도 없는 CWE는 `@취약점`에 번호 뒤에 적은 이름을 옮겨 쓴다(`@취약점{CWE-667 Improper Locking}` → "Improper Locking") |
| `@설명` | 코드내용 아래 설명 |
| **`@FA분석`** (분석, 사유) | FA분석 |
| **`@결론`** | 결론 |
| `@Ref` (참조) | 코드내용 아래 참조 |

### S-M 소스코드메트릭 → 소스코드메트릭 제한값 미달성 분석 보고서

매뉴얼 근거: 메트릭 제한값을 달성하지 못한 원인을 분석한 미달성 분석결과보고서(부록 7-12 5. 나).

| 항목 | 양식의 칸 |
|---|---|
| **`@메트릭`** | 메트릭. 종류는 사업마다 정하므로 값을 점검하지 않는다 |
| **`@제한값`** (기준) | 제한값 |
| **`@측정값`** | 측정값. 동일사항 위치마다 따로 쓴다 |
| **`@미달성사유`** (사유) | 미달성 사유 |
| `@설명` | 코드내용 아래 설명 |

### D 동적시험 → SW신뢰성 동적시험 미달성 분석 보고서

매뉴얼 근거: 설명자료(부록 7-16 5. 가·나). `@미달성사유`에는 다음 둘 중 어느 경우인지와 소스코드를 분석한 내용을 적는다.
(가) 방어 코드(Defensive Code)처럼 시험도구의 한계로 목표 실행률을 달성할 수 없는 코드, (나) 확장성을 고려해 작성한 코드.

| 항목 | 양식의 칸 |
|---|---|
| **`@커버리지`** (실행률, 기준) | 미달성 사유 칸의 첫 줄("코드 실행률 기준: 분기(Branch)"). `문장`, `분기`, `MC/DC` 중 하나(영문 `Statement`, `Branch`도 받음). 다른 값이면 경고 |
| **`@미달성사유`** (사유) | 미달성 사유 |
| `@요구사항` (Ref, 참조) | 미달성 사유 아래 관련 요구사항 |
| `@설명` | 코드내용 아래 설명 |

### 공통

| 항목 | 내용 |
|---|---|
| `@첨부` (근거자료) | 데이터시트 발췌, 다이어그램 등 근거 그림. 소스 파일 기준 상대 경로, `경로\|캡션`, 여러 개는 `;`로 구분. 그림 파일(png·jpg·jpeg·gif·bmp)만 되고, 소스 파일이 있는 폴더나 연 프로젝트 폴더 아래에 있어야 한다(절대 경로나 그 밖의 파일은 보고서에 넣지 않고 그 자리에 까닭을 적는다). 화면에서 넣은 그림과 다이어그램은 소스 파일 옆 `srt_attach/` 폴더에 저장된다(다이어그램은 `.png`와 원본 `.mmd`) |
| `@비고` | 동일사항 표의 비고. 위치마다 따로 쓴다 |

## 5. 도구가 점검하는 것

| 수준 | 내용 |
|---|---|
| 오류 | `START`/`END` 짝이 맞지 않음, 문법에 맞지 않는 `SRT-` 식별자, 인덱스 1 없음, 내용 없는 ID, 닫히지 않은 중괄호·주석 |
| 경고 | 굵은 글씨 항목 누락, 그 시험 유형에서 쓸 수 없는 항목, 동일사항 위치의 내용이 대표와 다름, 같은 ID를 다르게 씀, 주석 안의 `/*`·`//`(MISRA C:2012 Rule 3.1) |

오류가 있으면 종료 코드가 1이다. `--strict`를 주면 경고만 있어도 종료 코드가 1이다.

잘못 쓴 식별자와 항목 이름은 다음 모양까지 찾아내고, 고칠 수 있으면 올바른 표기를 제안한다.
확인·편집 화면의 "1 잘못 쓴 주석 고치기"에서 그 주석을 고쳐 소스에 반영할 수 있다.

| 잘못 쓴 예 | 제안 |
|---|---|
| `srt-s-c-id1-1` (소문자) | `SRT-S-C-ID1-1` |
| `SRT_S_C_ID1_1`, `SRT S-C-ID1-1` (밑줄, 빈칸) | `SRT-S-C-ID1-1` |
| `SRT-SC-ID1-1`, `SRT-S-C-1D1-1`, `SRT-D-ID-3-1` (빠지거나 틀린 글자) | `SRT-S-C-ID1-1`, `SRT-D-ID3-1` |
| `SRT-S-C-ID1-1STRAT`, `SRT-S-C-ID1-1 START` (START/END 오타, 빈칸) | `SRT-S-C-ID1-1START` |
| `@규측{…}` (항목 이름 오타) | `@규칙` |

올바른 태그의 본문(`{…}`) 안에 적은 다른 식별자나 파일 경로(`srt_attach/SRT-S-W-ID1_diagram1.png`)는 검사하지 않는다.
